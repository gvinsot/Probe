# SwiftProof v0.4.0

This release records more deterministic evidence and depends less on a model.
Changed and existing tests, and changed functions, can run on both revisions
without a model; recorded values can be compared instead of model-written
assertions; and exports contain only findings backed by recorded evidence. None
of the new records produces exit 1: only a reproduced high/critical hypothesis
does. The binding rules are in the
[v0.4 specification](../../../specs/swiftproof-v0.4-spec.md).

## Included

- `--deadline D` (from 1m to 24h) bounds dependency preparation, sandbox runs
  and the reviewer, and keeps 30 s to clean up and write the report. Running
  containers end as TIMEOUT, unstarted runs are recorded as SKIPPED, and the
  report records the deadline as an unverified area.
- One shared runtime budget: each sandbox run reserves its timeout before it
  starts, the new stages have sub-caps inside `sandbox.max_runtime_seconds`, and
  half of the budget is reserved for the reviewer's experiments when a reviewer
  runs. Dependency preparation has its own timeout instead.
- A single `divergences` list and an always-present **Behavior Divergences**
  section, shared by observation experiments and differential fuzzing. Each
  entry shows both recorded values and states that it does not establish which
  revision is correct.
- A reviewer call to a tool outside the offered set is audited as
  `rejected_tool_call`, with the requested name kept in its arguments, never
  as the audit tool name. The new v0.4 harness stages are audited under the
  reserved `stage:` prefix, which no reviewer call can produce. The initial
  checks and coverage keep their earlier audit names (`run_test`,
  `run_typecheck`, `run_build`, `run_coverage`), which the reviewer's tools of
  the same name also produce.
- The log of a candidate-side v0.4 check is written by candidate code, so its
  text never turns the check into ERROR (exit 4): only an infrastructure
  failure does, and a compile, setup or run failure stays FAIL.

- **Trusted dependency preparation** (`prepare` policy object,
  `--allow-prepare-network`). Before any candidate code, the base-branch
  policy's command runs once in one bounded container on the declared input
  files exported from the base commit, and the container is committed as a
  local image that every sandbox run of the review uses by ID. The image is
  keyed by the inputs, argv, user, network, env, base image ID, container
  arguments and SwiftProof version, and reused for the same base commit
  without starting a container. Network needs the policy and the flag, and
  never reaches checks. SwiftProof never pulls and never installs candidate
  dependencies; a candidate edit to a declared input adds a
  `prepare_input_changed` signal and an Unverified entry. `failed` and
  `not_permitted` run no check and exit 4. The prepared image is environment,
  not evidence: an equal key means equal inputs, not equal image content. See
  [dependency preparation](../PREPARE.md).
<!-- F8:end -->

<!-- F7:begin -->
- **Opt-in baseline execution cache (`--cache-dir DIR`).** A baseline-side run
  whose inputs are byte-identical to earlier runs is replayed once two live runs
  agreed on its result; candidate-side runs always execute. The key covers the
  baseline tree and staged tests, the command and complete sandbox arguments,
  the image ID the run executes, the Docker server, the policy's execution
  settings and the SwiftProof executable. A replay never supports a reproduced
  issue, a divergence or a `FAILS_ON_CANDIDATE` result: a replayed baseline is
  run again live before `REPRODUCED` is recorded. Negative conclusions resting
  on a replay are listed in `execution.replay_backed`. A replayed baseline FAIL
  is not run again, so a stale or forged entry can leave such a result
  unrecorded and lower the exit code (see the damage bound in the cache
  documentation). The directory must be outside the repository and the report
  directory, also through symlinks and Windows junctions (owner-only on Unix),
  or the review exits 3. Reviews of an updated pull request that share the
  directory replay unchanged baseline experiments. See
  [Execution cache](../EXECUTION_CACHE.md).
- Every review that creates a sandbox records an `execution` object: cache
  status and counters, the resolved image ID and Docker server identity,
  initial-check concurrency and the runtime budget spent.

- **Changed baseline tests** (`--base-tests`, review only, Go): the baseline
  version of the Go test functions of each changed Go test file that the
  change modified, removed or affected through the rest of the file (other
  declarations, imports, build constraints, a move to another directory) runs
  on the baseline tree and on a hybrid tree (the candidate with that
  package's test files and `testdata` reverted). Results are
  `FAILS_ON_CANDIDATE` (one recorded run each: possibly a behavior change
  accompanied by a test edit, possibly flakiness, for a human to judge),
  `PASSES_ON_CANDIDATE` or `UNVERIFIED`, recorded as `base_test_differential`
  evidence and in the new `base_tests` section. They never produce exit 1 and
  cannot support a hypothesis. No policy key; the flag needs a re-pinned
  workflow. See [changed baseline tests](../BASE_TESTS.md).
- **Lexical test-edit signals**, in `lint` and `review` without any flag, for Go,
  JavaScript/TypeScript and Python test files: `test_assertion_removed`,
  `test_case_removed`, `test_skip_added` and `test_expectation_relaxed`
  (medium) and `test_focus_added` (high). They are text heuristics, never
  evidence. Because `test_focus_added` is high, an added focus marker such as
  `it.only` now requests review (exit 2) under `--ci`.
<!-- F3:end -->

<!-- F6:begin -->
- **Impact analysis** (on by default in `lint` and `review`; `--impact=false`
  disables it). A static index of the repository's own Go packages, built from
  committed Git objects without running repository code or loading imports
  from outside the repository, lists the callers of each changed Go function
  in unchanged code and the existing tests that reach it within 3 references,
  labelled approximate. Callers become low `impacted_caller` review targets
  (at most 10 per function and 100 per run); one medium `analysis_limited`
  signal states what was left out. The reviewer's `find_references` and
  `inspect_symbol` use the index, and the new `find_callers` tool follows
  callers up to depth 3; each falls back to lexical search. It adds no policy
  key and never changes the exit code by itself.
  See [impact analysis](../IMPACT.md).
- **Impacted tests** (`review --impacted-tests`, opt-in). The reaching tests
  the index lists whose file the change did not modify (at most 16, from at
  most 4 packages) run on the baseline and on the candidate, inside a 180 s
  sub-cap. Each test gets one `impacted_test_differential` evidence record:
  `FAILS_ON_CANDIDATE`, `PASSES_ON_CANDIDATE` or `UNVERIFIED`, re-derived by
  `Finalize` from the recorded checks, never from a stored status. A failure
  is an outcome difference for a human to judge, not a reproduced issue: the
  static link is approximate. `FAILS_ON_CANDIDATE`, `UNVERIFIED`, a selected
  test without a result (including tests over the limits) and a stage that
  did not run request review (exit 2 with `--ci`), never exit 1; no signal
  kind is added. The flag exits 3 on `lint`, with `--checks=false` and
  with `--impact=false`. See [impacted tests](../IMPACT.md#impacted-tests---impacted-tests).

- **Observation experiments.** A generated test may record values instead of asserting them: Go through `t.Attr("swiftproof.<key>", value)` (Go 1.25 or later in the sandbox image), Vitest through `task.meta.swiftproof`. `run_generated_test` compares them key by key when the test passes on both revisions, runs one live baseline repeat when a key differs, and records a `differential_observation` evidence record (`DIVERGED`, `NOT_DIVERGED` or `UNVERIFIED`) next to the ordinary `differential_test` record.
- The new hypothesis status `DIVERGED`, the `divergences` array and the Behavior Divergences section show both recorded values for each validated divergence, with the note that this does not establish which revision is correct. A divergence requests review and never produces exit 1.
- A both-pass generated test whose recorded values differ, or cannot be shown equal (redacted, unconverted or unreadable), no longer supports `NOT_REPRODUCED`, and `NOT_DIVERGED` supports no hypothesis status.
- No policy key, flag or tool is added; the `create_test` and `run_generated_test` descriptions and the reviewer prompt describe the recipe. Jest templates record no observations. See [observation experiments](../OBSERVATIONS.md).

## Upgrading

**Upgrade in this order.** A pipeline pinned to v0.3.0 or earlier breaks the
moment a new key lands in its base-branch policy or a new flag is passed to it.

1. Publish v0.4.0, together with the updated report schema.
2. Re-pin every workflow that reviews your base branch to v0.4.0, updating the
   download URL and the pinned sha256 together (for example in your copy of
   `.github/workflows/review.yml`).
3. Only then commit a `fuzz`, `mutation` or `prepare` object to a base-branch
   policy, or pass a new flag: `--base-tests`, `--fuzz`, `--impact`,
   `--impacted-tests`, `--cache-dir`, `--parallel`, `--allow-prepare-network`,
   `--deadline`, `--report-url`, or `--format` with `sarif` or `pr-comment`.

A policy containing `fuzz`, `mutation` or `prepare` is **rejected with exit 3 by
every earlier binary**, because policy decoding refuses unknown fields, and each
new flag makes an earlier binary exit 3 while parsing arguments. `swiftproof init`
never writes the new keys. An earlier binary's `swiftproof report` silently drops
the new report fields and shows hypothesis statuses it does not know as
`UNVERIFIED`, so render reports with v0.4.0. Consumers that validate reports
against the v0.3 schema reject v0.4 reports; update the schema first. See
[CI integration](../CI.md).

Without any new key or flag, v0.4.0 still changes its output:

- JSON reports always contain the `intent_criteria`, `divergences` and
  `intent_test_failures` arrays, possibly empty, and lint and review reports
  contain an `impact` object unless `--impact=false` is passed.
- The Markdown report always contains a Behavior Divergences section.
- The initial checks are announced on one progress line, for example
  "Running test, typecheck, build in isolated Docker sandboxes...".
- The reviewer is offered a `find_callers` tool and may claim the `DIVERGED`
  status, which `Finalize` accepts only with validated observation or fuzz
  evidence.
- Every string kept from a Jest-compatible report is now redacted, and a report
  whose normalized results would still change under redaction is rejected as
  unreadable, which records its check as ERROR. Structured results are limited
  to 16 MiB per report, of which candidate-side runs may use at most half.
- Redaction is repeated until the text no longer changes; v0.3 made a single
  pass, which could leave text that a second pass would still change. Text that
  would need more than 8 changing passes is masked as a whole.
- A generated-test evidence record whose test names or test path would be
  changed by redaction, or contain the redaction marker, supports no
  hypothesis: a re-rendered report could otherwise select different results.
  A high reproduced claim resting only on such a record is now `UNVERIFIED`,
  which is exit 2 with `--ci` instead of exit 1.
- In Recorded Evidence, a stored evidence status that the report did not
  re-derive from the recorded checks is marked "as stored; not accepted as
  evidence".
- A `DIVERGED` claim is kept only when the evidence it cites is listed under
  Behavior Divergences, and that section no longer says values were equal
  when an observation or fuzz record was inconclusive or not accepted.
- A reviewer-requested run whose reviewer time limit expired before it started
  is recorded as SKIPPED, with a text naming that time limit, instead of
  TIMEOUT; it still requests review with `--ci`.
- Under `--ci`, a configured `fuzz` or `mutation` stage, or a requested
  `--base-tests` or `--impacted-tests` run, that did not run requests human
  review (exit 2).

## Installation

Download the archive for your operating system and architecture, verify its entry
in `SHA256SUMS`, extract it, and put `swiftproof` (`swiftproof.exe` on Windows) on
your PATH. Run `swiftproof version` to verify installation.

Git is required. Docker with Linux containers is required only for executing
repository code, including dependency preparation. Go is not required to run the
downloaded CLI.

## Current limits

Behavior divergences, tests that fail on candidate code, intent-test failures and
surviving mutants ask for human judgment. None of them establishes which revision
is right, and none produces exit 1. SwiftProof makes no equivalence,
completeness or mutation-score claim, and a report with no finding is not an
approval.

This remains a 0.x release: signals and passing checks are not a correctness
guarantee and never automatically approve or merge a pull request. Archives are
not signed or notarized. See README.md and SECURITY.md for setup and execution
boundaries.
