# Security boundaries

SwiftProof treats candidate code, generated tests, model output and repository text as untrusted. Static analysis uses immutable Git objects with external diff/textconv disabled. Execution uses Docker only; the source checkout is never executed or mounted.

Policy comes from the tip of the base ref (`--base`, `main` by default) unless the caller explicitly supplies `--config`; the report records that commit. The diff still starts at the merge base, but the policy never comes from the candidate or from any commit only the candidate branch contains. The base ref is a trust decision: select a protected branch or trusted commit, never a branch the change author can write to, and pin the binary used in CI. Candidate policy changes cannot implicitly alter image, commands, provider or budgets. A nonempty `reviewer.model` in this trusted policy enables provider requests automatically during `review`. Use `--reviewer=false` to disable them for a run. `lint` never calls the provider. `--no-network` applies only to sandbox containers.

The process environment is the second trusted input, at the same level as the pinned binary: `SWIFTPROOF_REVIEWER_ENDPOINT`, `SWIFTPROOF_REVIEWER_MODEL` and the API key (variable, `<NAME>_FILE`, or the Docker secret at `/run/secrets/<NAME>`) override the policy's provider, and a model supplied this way enables provider requests exactly as a policy model does. Whoever can set that environment can therefore choose where redacted source context is sent, so it belongs to the deployment operator and not to the reviewed change; candidate commits, PR branches and untrusted forks never reach it. Image, commands, budgets and sensitive paths remain policy-only. The credential is read at most once per run, is never written to a report, and the run log names only its source.

Containers use a non-root UID, `--network none`, read-only source/root mounts, bounded tmpfs workspace, `--cap-drop=ALL`, `no-new-privileges`, CPU/memory/PID limits and forced cleanup. These controls follow the [Docker run reference](https://docs.docker.com/reference/cli/docker/container/run/) and [network isolation documentation](https://docs.docker.com/engine/network/drivers/none/). Docker shares a kernel; hostile multi-tenant submissions may require disposable VMs. See [Docker Engine security](https://docs.docker.com/engine/security/). The optional dependency-preparation container is the one exception: it has a writable root filesystem, may run as root when the trusted policy says so, and has network only when the policy and `--allow-prepare-network` both allow it. Its full profile is in [dependency preparation](PREPARE.md).

Trust the preloaded image and its environment, files and dependencies. Never bake credentials into it. SwiftProof never pulls images. It installs dependencies only when the trusted base-branch policy defines a `prepare` command, which runs on inputs exported from the base commit before any candidate code; candidate dependencies are never installed. Compromised dependencies can influence experiments; tests remain observations, not mathematical proofs.

Known credential paths are excluded from readable/executable snapshots. Common tokens, passwords and private-key patterns are masked in outputs, reports and provider context. This is best effort: custom secret formats, encodings and deliberate transformations may escape masking. Avoid remote reviewers when transmitting source is unacceptable.

A coverage profile is written by the candidate revision's own test suite and is untrusted input. It can move verdicts in both directions: fabricated execution suppresses a signal, and fabricated non-execution manufactures one. Coverage data may therefore add signals and add sentences; it may never delete a signal, lower a severity, support a dismissal or mark anything resolved, and no conclusion is drawn from a line being executed. The profile leaves the sandbox only as a length-declared framed payload on the container's standard output, separately bounded and derived from `sandbox.max_output_bytes`; repository code gains no writable host path, no volume and no container that outlives the run.

Generated tests create new test paths only and run against separate baseline/candidate copies. A misleading assertion can cause a differential failure; humans must evaluate its relevance. Recognized build/setup failures, timeouts, missing dependencies and inconclusive baseline failures do not establish a reproduced behavioral issue. Arbitrary framework output cannot always be classified reliably.

Providers have no unrestricted shell or URL fetcher. All functions and responses are bounded. HTTPS is required remotely, redirects and environment proxies are refused, and HTTP is limited to loopback. The integration follows the [function-calling protocol](https://developers.openai.com/api/docs/guides/function-calling).

Reports/hashes are unsigned. Someone able to edit JSON can forge evidence. Check provenance through trusted CI storage and immutable commit IDs; `swiftproof report` only renders. Output directories must be trusted and should not be shared with other writers during review.

Normal completion/cancellation cleans temporary files and containers. Power loss or abruptly killing the host can leave resources behind; container names begin with `swiftproof-` for administrative inspection. Retained redacted artifacts deliberately remain in the chosen report directory. Two other outputs persist by design and only when requested: images derived by a policy's `prepare` command, and the entries of an explicit `--cache-dir`.

## Evidence added in v0.4

New evidence may add review requests. It never suppresses, lowers or dismisses anything a live execution recorded. The only v0.4 conclusion that can rest on a non-fresh execution is a negative one backed by an opt-in cache entry that two live runs agreed on; the report lists it in `execution.replay_backed`.

Repository code executing in the sandbox can write every channel that carries its results back:

- the check log (standard output and standard error, bounded and redacted), which also carries `go test -json` events such as Go `t.Attr` observations;
- the single payload file a run may return on the length-declared framed channel: a coverage profile, a Jest-compatible report written to `{results_out}` (including Vitest `task.meta` values), or a fuzz observation stream.

These structured values are kept apart from the log so log text cannot impersonate them; code executing in the sandbox can still write them. A status derived from them, such as `NOT_REPRODUCED`, `NOT_DIVERGED`, `PASSES_ON_CANDIDATE` or `INTENT_TEST_PASSED`, describes the recorded run only and is not tamper-proof. Every recorded `results` value is unchanged by redaction, and structured results are limited to 16 MiB per report; larger ones are kept only as hashed artifacts. Candidate-side runs may fill at most half of that limit, so candidate output cannot use up the part that baseline-side captures need. A candidate-side Jest-compatible report that exceeds its half is still recorded as an ERROR check, as a missing or unreadable report is; this is a known operational limit, and a fuzz observation stream that exceeds it makes its function inconclusive instead.

Candidate code also writes the logs of the candidate-side v0.4 checks (fuzzing, changed baseline tests on the hybrid tree, impacted tests on the candidate, and mutation). Their log text therefore never makes a check ERROR, which would be exit 4; only infrastructure failures do. The v0.2 log-text rules still apply to the v0.2 check kinds and to generated tests, including intent tests.

Models still create no evidence. A model may propose hypotheses, write tests and attach a labelled judgment to a divergence, but only the harness records checks and evidence, and `report.Finalize` re-derives every status from the recorded checks, including when `swiftproof report` re-renders a saved report.

**Dependency preparation.** Only the trusted policy (the tip of `--base`, or `--config`) can define `prepare`; a candidate edit to `.swiftproof.json` cannot add, change or enable it. Its container sees only the declared input files, exported as exact blobs from the review's base commit, never from the head commit, through one read-only bind mount; credential-bearing names are refused, and no Docker socket, host environment, credential or writable host path is ever given. It runs before any candidate code, from the local sandbox image resolved to its ID, never pulls, drops every capability (a fixed six are added back only for `user: root`), sets no-new-privileges and keeps the sandbox memory, CPU, PID and output limits; only its root filesystem is writable. The created container's mounts are checked, so a sandbox image that declares a `VOLUME` fails the stage. The container has no tmpfs: everything the command and its lifecycle scripts write, including `/tmp` and its `HOME` (`/swiftproof/home`), is committed into the derived image, counts toward `max_added_mb` and can be read by anyone with the image. With `user: sandbox`, `/swiftproof/home` belongs to UID 65534, the identity checks run as, so code under review can read it even though checks do not use it as `HOME`. The command must leave no token or credential anywhere in the container, including anything a lifecycle script fetched from a reachable metadata endpoint. The network needs both the policy's `prepare.network` and `--allow-prepare-network`, `--no-network` always wins, and that permission never reaches checks, which keep their unchanged profile. Lifecycle scripts run by the command, with network when permitted, can alter the derived image that every check then uses: the same trust level as a manually built image, now keyed, labelled and logged. Prefer hash-pinned lockfiles and flags that skip install scripts, and restrict egress (cloud metadata endpoints and the runner's local network are reachable otherwise). The image's labels are unsigned local metadata that anyone with daemon access can forge. Every failure runs no check and exits 4, with no fallback to the unprepared image. Candidate dependency changes are never installed; they add a `prepare_input_changed` signal and an Unverified entry. See [dependency preparation](PREPARE.md).

**Execution cache (`--cache-dir`).** Only the SwiftProof process reads or writes the cache; containers never see it, and the sandbox keeps its single read-only snapshot mount. Only baseline-side runs on the pristine baseline snapshot (plus files a stage staged, which are hashed into the key) and without network are eligible; candidate-side runs are never read from or written to it, so candidate code cannot feed a later baseline result through it. The key commits to the baseline tree, the command and the complete sandbox argument vector, the image ID the run executes, the Docker server identity, the trusted policy's execution settings and the SwiftProof executable. The directory is validated before any container starts: outside the repository and the report directory after the symlinks and Windows junctions on its path are resolved (existing directories are also compared by file identity), not itself a link or reparse point, and owner-only on Unix (Windows ACLs are not checked). Every read re-checks the content hash, the key recomputed from the stored preimage, strict decoding, bounds and age, and removes a file that fails; this detects corruption, not forgery, so the directory is a trusted input. A replay never supports a positive status: the harness re-runs a replayed baseline PASS live before recording `REPRODUCED`, and `Finalize` refuses a replayed baseline for every positive status. In this build a replayed baseline FAIL is served and not run again, so a stale or forged FAIL entry can leave `UNVERIFIED` an experiment that a live baseline would have recorded as `REPRODUCED`, a divergence or `FAILS_ON_CANDIDATE`, and can lower the exit code; the replayed check is marked in the report, and [Execution cache](EXECUTION_CACHE.md#trust-and-privacy) states this damage bound. Entries hold the recorded, redacted log and a payload only when it is complete and unchanged by redaction, never raw output; they are written with mode 0600 and are never uploaded by SwiftProof.

**Changed baseline tests (`--base-tests`).** Selection parses committed blobs with `go/parser` and never executes repository code. The hybrid tree is assembled on the host from the already sanitized snapshots: a private copy of the candidate tree in which one package directory's `*_test.go` files and `testdata` are replaced by the baseline's. Secret-bearing file names stay excluded, symlinks are never created or followed, every path is checked, files are created exclusively, and the copy is deleted after the stage; a hashed manifest records what it removed and restored. A candidate entry that blocks a baseline path (a directory named like a baseline test file, a file where a package directory was) is removed and recorded, so the shape of the candidate tree cannot turn the stage into an operational failure (exit 4); the audit record of a directory that still cannot be reverted names no host path. Both runs use the unchanged check profile and add no mount, volume, network or payload channel. Baseline test code runs against candidate code inside the same sandbox, as generated tests already do. Candidate code writes the hybrid run's log: it can make a baseline test appear to pass, so `PASSES_ON_CANDIDATE` is an observation only, while a forged pass after a real failure makes the result `UNVERIFIED`, and forging a failure only adds a review request. A replayed baseline run never supports `FAILS_ON_CANDIDATE`. The flag is set by whoever invokes SwiftProof; the candidate branch can influence only which of its baseline tests are selected, within fixed limits.
<!-- F3:end -->

<!-- F6:begin -->
**Static impact index (F6).** `lint` and `review` parse and type-check untrusted committed Go source in the SwiftProof process, with the Go standard library only. The index reads Git objects of the candidate commit (and of the base commit for changed files) through the same bounded tree and blob readers as snapshots, skips symlinks, submodules and the paths snapshots exclude, and never runs the go command, cgo, code generation, build scripts or any network access; imports from outside the repository are not loaded. Its work is bounded: 64 MiB of source, 5,000 packages and 2,000,000 references; a 120 s limit checked between packages, on every type error, and during the impact searches before every interface-implementation check; a bound on the estimated `go/types` cost of each implementation check, above which the check is not made and the section is `limited`; a visit budget for each impact search; and a work budget and a 10 s limit for each reviewer tool query. The type check of one package that produces no type error is not interrupted. Some `go/types` work grows faster than the source (for example selectors on a struct that embeds thousands of types), so a small crafted package can keep that check, and the process, busy past the 120 s limit, and Ctrl-C does not stop it before the check ends. A panic inside `go/types` is recovered per package and reported as `limited`. `//line` directives are ignored, so the candidate cannot move a recorded site to another file name or line, for example into a `_test.go` name that would hide a caller. Because the candidate controls what is indexed, it can hide callers or add reference sites: the index may therefore only add low-severity `impacted_caller` signals, one medium `analysis_limited` signal and tool observations. It never creates evidence, never removes or lowers a signal, and never supports a dismissal or a `NOT_REPRODUCED` claim. Tool snippets are taken from the redaction of the whole file, as `read_file` shows it, and report strings are redacted.

### Differential fuzzing (F2)

- **Host side.** Selection and rendering only parse and print Go source (`go/parser`, `go/format`, and `go/build.MatchFile` over in-memory files). No repository code runs on the host. Repository code runs only through the check sandbox, with the reviewed `generated_test` command; fuzzing adds no mount, volume, Docker flag, environment variable or command key.
- **Harness integrity.** The harness file is rendered from fixed template text, `strconv` literals and identifiers that the package declares, each re-checked as an identifier. Every identifier the file declares carries a suffix drawn at random for each run, so code under review cannot declare a colliding name in advance. The file is written without overwriting anything on both revisions, runs byte-identical on both, and is removed afterwards.
- **Observation stream.** Each revision writes its own stream from inside its own process. Code under review can therefore suppress, pad or fabricate the observations of its own revision: it can hide a divergence, or show one that is itself behavior of the candidate. It cannot write the baseline's stream or change the comparison. The host accepts a stream only when every line is the byte-exact canonical form of one record in the expected order, and rejects the whole stream otherwise. It keeps only redacted display cuts of at most 256 bytes and compares SHA-256 hashes computed in the sandbox, so redacting a display never changes the result of a comparison. A display that redaction would still alter once escaped as JSON is replaced by `[REDACTED]` as a whole. The stored stream puts every field on its own line, so that no redaction rule can match across fields, and it must be unchanged by redaction; a stream that is not is rejected, and every function of its package is then inconclusive.
- **Hashes of returned values.** The report keeps the SHA-256 and the exact byte length of every recorded encoding, including encodings whose display was redacted because it looked like a credential. The hash is not salted and the encoding format is public, so a low-entropy value that the code under review returned (a short password, a PIN) can be recovered from the report by hashing guesses. Redacting the display does not protect such a value. Handle the report of a run whose changed functions may return real secrets as you would those secrets.
- **Derived outcomes.** Every outcome is derived only from the recorded checks (status, log and normalized stream) by one comparison, so deriving it again from a saved report shows whether the recorded checks support the stored outcome, and an edit that breaks a stream's structure rejects the stream. The comparison reads hashes, lengths, indices, flags, function states, commands, check kinds and the test outcomes in the logs. A consistent edit of those records gives the outcome they describe and is not detected. Display values, the counterexample text and log lines that decide no test outcome are not protected at all: editing them leaves the outcome unchanged while showing other values. Reports stay unsigned: a consistent forgery of the whole JSON remains possible.
- **Models** cannot start, parameterize or read a fuzz run before its evidence exists. No reviewer tool starts one.

<!-- F4:begin -->
**Mutation of added lines.** Only the trusted policy (the tip of `--base`, or `--config`) can enable `mutation` or choose its command and budgets; a candidate edit to `.swiftproof.json` cannot. The command must be `go test -json` with one standalone `{package}` and flags only, and flags that change the directory, the executed binary or the test selection are refused; `{package}` comes from a validated diff path and always starts with `./` or is `.`, and nothing runs through a shell. Mutants are found on the host by parsing bounded snapshot bytes with `go/parser`; repository code is never executed or type-checked with importers to find them. Every control and mutant runs under the unchanged sandbox profile in a private copy of the sanitized candidate snapshot, never in the candidate or baseline snapshots: a mutant overwrites one existing regular file only after its content matched the planned original, and the original is written back and read again; any mismatch or failure aborts the stage before another run and exits 4. Logs and patch artifacts are bounded, redacted and hashed. The candidate controls its own tests, and code executing in the sandbox can write the `go test -json` log the outcomes are read from (through the framing marker of `test2json` or the standard output of the `go` process), so it can force any mutant status: killed, invalid, timed out or inconclusive only remove claims or request review, and a forced survivor only adds review signals against the candidate. Mutation therefore adds signals and sentences only: it never deletes a signal, lowers a severity, supports a dismissal, creates evidence or influences a hypothesis. See [mutation of added lines](MUTATION.md).
<!-- F4:end -->

<!-- F1:begin -->
**Observation experiments.** A generated test's recorded values (Go `t.Attr` events in the check log, Vitest `task.meta` in the structured results) are written by code executing in the sandbox, and `report.Finalize` re-derives every observation record from the recorded checks. Ordinary output cannot create a Go observation: only a line carrying the test runner's framing byte becomes an `attr` event. Code under test that prints such a line can add a key or duplicate one; a duplicated key is never compared, so a forged line can turn a divergence into `UNVERIFIED` but cannot produce `NOT_DIVERGED` for that key. Code that sabotages its own test process can forge anything a passing test can, as for `NOT_REPRODUCED`. Values are redacted before they are parsed, compared, displayed or sent to a provider; equal redacted values, and values that redaction would alter after decoding, are never compared. A divergence needs a live baseline repeat that agrees with the first baseline run, never a replayed one. Observations only add review requests: `NOT_DIVERGED` supports no hypothesis status. A recorded difference withdraws the `NOT_REPRODUCED` of the same generated test instead of hiding behind it, and so does anything that leaves equality unknown: a redacted key or value, a value the runner could not convert, or observations that could not be read. Code under test that makes its own value unreadable or oversized therefore adds a review request; it cannot hide a difference that way.
<!-- F1:end -->

<!-- F5:begin -->
**Intent criteria and intent tests.** The intent is untrusted caller or PR-author input. It must be UTF-8 without NUL, SwiftProof's own PR-comment blocks are removed from it, it is redacted before it is recorded, hashed (`intent_sha256`) and parsed, so the hash never covers a secret that the recorded intent hides, and its criteria are data: they are redacted, escaped in Markdown, sent to the provider inside the untrusted review data, and never change a command, image, network setting, budget or provider setting. An intent test runs the trusted base-branch `generated_test` command in the ordinary sandbox, on the harness's private candidate copy only; the file is placed with the same path, overwrite and symlink rules as generated tests and removed after the run, and the working checkout and the base snapshot are never modified. Models cannot create intent evidence: only the harness records `intent_test` records and `generated_test_intent` checks, and `report.Finalize` re-derives each status from the recorded check, the recorded diff and the record's referenced symbols, including on re-render. The failure channels (the Go test log, the Jest-compatible report) are written by code executing in the sandbox, so an intent status is not tamper-proof. Code under test can turn a failure into `UNVERIFIED`, fake one that still requests only human review, or make its intent check ERROR (exit 4) by writing one of the inherited setup-failure markers (such as `permission denied` or `command not found`) into the log or by breaking the runner's output framing, which also hides the intent-test failure; it can never produce exit 1. The host-side linking of an intent test to the change is computed once per run and stays linear in the size of the diff. `intent_judgment` is never read by any status, list, severity, target or exit-code computation, so an attacker-written intent can earn at most a labelled model opinion next to a divergence.
