probe version
  • lint analyzes a change statically. It never executes repository code and never calls an AI provider.
  • review adds sandboxed checks in Docker, the opt-in evidence stages (changed baseline tests, impacted tests, differential fuzzing, mutation, dependency preparation) and, when a model is configured, an AI investigation. review --read-only keeps only the AI investigation, with read-only tools and no Docker.
  • plan asks the configured provider for an implementation plan before any code is written, evaluates it with fixed rules, and turns it into a contract that lint --plan and review --plan check the diff against.
  • knowledge, context and graph manage what the AI reviewer reads besides the diff: the codebase knowledge base, the other repositories and the repository graph.
  • login connects the machine to a Probe Hub account, so that the AI reviewer uses the hub's LLM when no provider is configured; logout revokes that access. See probe login.
  • Only committed files are analyzed; uncommitted edits and untracked files are ignored.
  • Reports are written to .probe/ in the repository by default. Console output stays short.
  • Flags accept one or two dashes (-ci or --ci). Booleans are set with --ci or --ci=true and cleared with --checks=false. A value is given as --base main or --base=main.
  • Run probe <command> --help for the flags of a command.

Choosing revisions

Both sides of a comparison resolve to immutable commit IDs, recorded in the report. Renames, deletions, binary files and file type changes are handled.

FormCompares
--base main (default)From the merge base of main and --head to --head, like a pull request. Commits added to main since the branch point are not part of the change.
--base main --exactFrom the tip of main directly to --head.
BASE..HEADThe two exact commits, for example HEAD~1..HEAD to review the last commit. Overrides --base, --head and --exact.
BASE...HEADFrom the merge base of the two revisions to HEAD.

A range may appear before or after the flags: probe review main..HEAD --ci and probe review --ci main..HEAD are equivalent. At most one range is accepted. Any revision Git understands works: branches, tags, origin/main, HEAD~3 or a commit ID. CI jobs need enough history to resolve the base (for example fetch-depth: 0).

The trusted policy is always read from the base branch, never from the change under review, so a pull request cannot loosen its own rules.

probe lint HEAD~1..HEAD                 # the last commit
probe lint --base origin/main --ci      # this branch as a pull request, for CI
probe lint --base main --format json    # JSON report only
probe lint --base main --plan .probe/PLAN.json   # scope drift against an approved plan

probe review

Everything lint does, plus the policy's test, typecheck, build and coverage commands in disposable Docker containers, plus an AI investigation when a model is configured. Requires Docker with Linux containers and a preloaded sandbox.image.

--base REVmainBase branch or revision. The comparison starts at its merge base with --head; its tip supplies the trusted policy.
--head REVHEADCandidate revision under review.
--exactfalseCompare the base revision itself instead of the merge base.
BASE..HEAD—Positional range; see Choosing revisions.
--repo PATH.Repository directory.
--config PATHpolicy of the baseUse this local policy file instead of .probe.json from the base branch, for example to try a policy before committing it. Only pass a file you trust: it decides what runs and where source is sent.
--out DIR.probeReport directory, relative to the repository root. Artifacts go to DIR/artifacts/.

--cifalseExit with code 2 when human review is required, including high-risk signals, unverified areas or incomplete checks.

--read-onlyfalseInvestigate with the deployment's model and read-only tools only, without Docker or code execution. See Read-only review.
--ai-impacts-criticalitytrueA linter signal the reviewer read as no_risk, citing a recorded source read, drops one severity level; a low one is set aside. --ai-impacts-criticality=false keeps the linter's severities. See signal assessments.
--swarm, --swarm-agents LISTpolicy reviewer.swarmInvestigate with specialized agents in parallel instead of one reviewer; --swarm-agents picks them and implies --swarm. Refused with --reviewer=false. See Reviewer swarm.

--max-iterations Npolicy (20)Override reviewer.max_iterations for this run, 1 to 100.
--intent TEXT—Pull request intent or acceptance criteria (at most 64 KiB). Recorded in the report and given to the reviewer.
--intent-file PATH—Read the intent from a UTF-8 file. Cannot be combined with --intent.
--jira KEY, --linear KEY, --notion PAGES, --gdoc DOCS—Add a Jira or Linear issue (auto: the key in the branch name or commit messages), up to 5 Notion pages or up to 5 Google Docs to the intent. A failure to fetch exits 3 before anything runs. See Intent from Jira, Linear, Notion and Google Docs.
--rules TEXT, --rules-file PATH—Team coding rules (UTF-8, at most 32 KiB) the reviewer checks the changed code against. See Coding rules.
--feedback-file PATH—JSON summary of the team's reactions to earlier findings (at most 64 KiB), written by Probe Hub. Guidance for the model, never evidence. See Team feedback.
--knowledge PATHPROBE_KNOWLEDGE.mdThe knowledge base, read at the tip of the base branch and given to the reviewer, which proposes updates. none disables it.
--context-dir DIR, --context-repo NAME=PATH—Where the checkouts of the context repositories are: DIR/owner/repo or DIR/repo, or one path per repository (repeatable).
--fetch-contextfalseShallow-fetch a context repository that has no local checkout from the url the policy gives.
--clusters FILE—Operator JSON file of repository cluster definitions shared by an organization.
--contexttrue--context=false ignores the cross-repository context the policy declares for this run.
--allow-networkfalseGive sandbox containers network access. Takes effect only if the trusted policy also sets sandbox.network: true.
--no-networkfalseForce sandbox networking off. Does not affect reviewer API calls; add --reviewer=false for that.
--plan PATH—Check the diff against the contract of a PLAN.json. A drifted change requests human review (exit 2 with --ci), never exit 1.
--impacttrueBuild the static impact index of changed functions. --impact=false skips it (and cannot be combined with --impacted-tests).
--graph, --graph-cache DIRtrue, user cacheBuild the repository graph and give it to the reviewer; --graph=false skips it, --graph-cache off disables its cache.
--impacted-tests v0.4falseRun the unchanged tests that the impact index lists as reaching a changed function, on baseline and candidate: Go tests, or TypeScript/JavaScript tests with a Vitest or Jest generated_test template. A test passing on the base and failing on the candidate is FAILS_ON_CANDIDATE: a reason to review, not a defect.
--base-tests v0.4falseRun the baseline version of each test the change modified or removed, on baseline and candidate code: Go test functions, or TypeScript/JavaScript test() and it() calls with a Vitest or Jest template.
--fuzz v0.4trueRun the differential fuzzing that the policy's fuzz object configures. --fuzz=false records the stage as disabled.
--cache-dir DIR v0.4—Opt-in cache of baseline executions, outside the repository and the output directory. A replayed baseline run never supports a positive result.
--parallel N v0.41Run the initial checks N at a time, 1 to 4.
--deadline D v0.4—Overall time limit of the run, from 1m to 24h; 30 seconds of it are kept for cleanup and the report.

probe review --base main --ci                        # typical pull request run
probe review HEAD~1..HEAD --reviewer=false           # checks only, no provider
probe review --base main --checks=false --reviewer=false   # static only, like lint
probe review --base main --intent-file PR.md         # give acceptance criteria
probe review --base main --impacted-tests --base-tests --ci   # run tests on both revisions
probe review --base main --jira auto --ci                # the Jira issue named by the branch is the intent
probe review --base main --swarm                         # specialized AI agents in parallel
probe review --read-only --base main --ci                # AI review without Docker or execution
probe review --base main --format markdown,json,sarif,pr-comment --report-url "$RUN_URL"

Dependency preparation runs first, when the policy has a prepare object. Checks then run in the order test, typecheck, build, then coverage, followed by the evidence stages and the reviewer. Each container is non-root, has a read-only root and source mount, no added capabilities, no network by default, and the CPU, memory, PID and time limits of the sandbox policy. The Docker socket, your working checkout and API keys are never mounted. If Docker or the image is missing, the run ends with exit 4; nothing ever falls back to your host.

probe plan

Before the change is written: the configured provider simulates, read-only, how it would implement an intent at the base commit and submits a structured plan (files, symbols, dependencies, steps). Probe evaluates it with fixed rules and writes PLAN.json and PLAN.md. The model produces the plan; it never judges its risk. Nothing is modified or executed.

FlagDefaultDescription
--intent-file PATH, --intent TEXT—The change to plan. Required, unless an issue or document below supplies it; at most 64 KiB of UTF-8, read like the review intent.
--jira KEY, --linear KEY, --notion PAGES, --gdoc DOCS—Plan from a Jira or Linear issue, Notion pages or Google Docs, alone or with an intent; auto reads the key from the branch name. See Intent from Jira, Linear, Notion and Google Docs.
--base REVmainThe revision the plan starts from. Its tip supplies the trusted policy.
--config PATHpolicy of the baseExplicit trusted local policy.
--out DIR.probeOutput directory, relative to the repository.
--cifalseExit 2 when a category is flagged or something was left unverified.
--max-iterations NpolicyOverride the provider iteration budget, 1 to 100.
--reviewertrueA provider is mandatory: without a configured model, or with --reviewer=false, plan exits 3 and writes nothing.

The planner's tools are read-only and work on a snapshot of the base commit: list_files, read_file, search_code and the index-backed find_references, inspect_symbol and find_callers, then submit_plan once. The assessment flags four categories from the plan and the base commit only:

CategorySignals
Critical partsplan_critical_path (a planned path matches sensitive_paths), plan_sensitive_symbol (an authentication, authorization or payment name).
Architectureplan_exported_signature, plan_dependency_change, plan_new_package.
Regression riskplan_wide_impact (10 or more callers), plan_untested_impact (callers and no reaching test), measured on the static index of the base commit.
Other major changeplan_file_deletion, plan_large_scope (20 or more files), plan_inconsistent, plan_unmeasured.

Exit codes: 0; 2 with --ci when a category is flagged; 3 usage or configuration; 4 provider failure or no accepted plan.

Scope drift: --plan

lint --plan and review --plan read the plan's contract and compare the real diff with it. Each difference in the diff also becomes a plan_drift signal. The section is drifted when an item is medium or higher.

ItemSeverityWhen
unplanned_filemediumA changed file the plan does not list (unplanned_test_file, low, for a test file).
unannounced_exported_changehighAn exported Go declaration changed or removed without being announced as signature or remove.
unannounced_critical_pathhighA changed path matches a critical glob of this review's policy and the plan did not list it.
unannounced_dependency_changemediumA dependency manifest changed without being declared.
planned_file_untouchedlowA planned file the change does not touch (section only).
 
probe plan --intent-file task.md --ci                     # 1. plan; exit 2: a human validates it
# 2. an agent implements the plan
probe review --base origin/main --plan .probe/PLAN.json --ci   # 3-4. exit 0: merge; exit 2: review

The plan gate

review --plan ends with a decision, plan_drift.decision, printed on stdout and at the top of the Plan Conformance section. With --ci, it is the exit code.

DecisionWhen
no_human_review_required (exit 0)All of: the plan, re-assessed by the review from its proposal at its base commit with this review's trusted policy, flags no category and has no measurement gap; the change conforms to the plan and to its base; at least one check ran and all passed; no reproduced issue, high or critical signal, unverified area or other section requesting review.
human_review_required (exit 2)Anything else. Every reason is listed in plan_drift.decision_reasons. lint --plan runs no check, so it always requires review.

The flags and contract stored in PLAN.json are never trusted: the contract is re-derived from the proposal, so an edited plan cannot widen the scope unassessed, and probe report recomputes the decision from the recorded report. The gate is a process decision, not a verdict on correctness. A plan that raises nothing is not proof that the change is safe, and drift does not check that the change implements the intent. See pre-change plans and the CI recipe.

FlagDefaultDescription
--repo PATH.Directory in which to create .probe.json.
--language NAMEdetectedgo, typescript, javascript, python, rust or unknown. Detected from go.mod/go.work, Cargo.toml, tsconfig.json, package.json, then pyproject.toml/setup.py/requirements.txt. Selects the defaults.

probe knowledge

Maintain PROBE_KNOWLEDGE.md, an editable Markdown knowledge base of the repository: how parts work and relate, known risks, architecture and conventions, one entry per ## heading. A review reads it at the tip of the base branch, like the policy, so a change never supplies the knowledge its own review receives, and gives the reviewer the entries whose paths match a changed file, within 24 KiB. They are context for the model, never evidence or instructions.

CommandDoes
probe knowledge build [--base main] [--focus TEXT]The configured provider explores the base commit with read-only tools and proposes entries, for example to bootstrap the file. Nothing is written to the repository or executed. Needs a model (exit 3 otherwise).
probe knowledge apply [--from .probe/knowledge-updates.json]Merge the proposed additions, corrections and removals into the working-tree file, keeping your manual edits. Review the diff and commit it: Probe never commits.
probe knowledge check [--knowledge PATH]Validate a hand-edited file: unique titles, known kinds, no stray heading outside code fences, size limits. Exits 1 on a problem.
 
## Refunds are validated by the gateway
- kind: architecture
- paths: pay/**, gateway/refund.go
- updated: 2026-09-30 (review of 1a2b3c4d)

The refund handler trusts the amount because the gateway checks it first.

Kinds are component, relationship, risk, architecture, convention, review and note. During a review, the reviewer may propose up to 20 updates with its record_knowledge tool; they are recorded in the report and written to .probe/knowledge-updates.json, with a merged preview in .probe/KNOWLEDGE.md. review --knowledge none disables the knowledge base.

probe graph

The repository graph of a whole commit, not only the diff: components, packages, files, functions, types and external dependencies (go:, npm:, pypi:, cargo:), linked by contains, calls, member_of, implements, imports, depends_on and declares edges. lint and review build it by default (--graph), from Git objects only, and record its summary and its structural delta against the base: new external dependencies, new dependencies between components or packages, added or removed types. It adds no signal and never changes the exit code.

probe graph build [--commit HEAD] [--out graph.json]          # build (or read from the cache), optionally export
probe graph query search Cart.Total [--kind function]
probe graph query neighbors internal/payment --kinds depends_on --direction in --depth 2
probe graph query path api.Handle Cart.Total [--undirected]

The reviewer queries the same graph with graph_search, graph_neighbors (up to 3 hops) and graph_path. Graphs are cached by commit in the user cache directory, or in --graph-cache DIR (off disables it); in CI, keeping that directory between runs reuses the base graphs. An edge is a place to look and a missing edge is not proof that none exists: function values, reflection and generated code are not resolved. See repository graph.

probe report

Re-render a saved JSON report, for example to regenerate Markdown or produce SARIF in CI. Nothing is re-run, and re-rendering does not authenticate the evidence it contains; every status is re-derived from the recorded checks, so an edited report is corrected rather than trusted.

FlagDefaultDescription
--input PATH.probe/confidence-report.jsonSaved JSON report (version 1, at most 64 MiB).
--out DIR.probeOutput directory, relative to the current directory.
--format LISTmarkdown,jsonComma-separated formats to write: markdown, json, sarif v0.4, pr-comment v0.4, pr-summary.
--report-url URL v0.4—An https link to the full report, cited in PR_COMMENT.md.

probe login and probe logout

Use the LLM of a Probe Hub instead of a provider account of your own. probe login prints a link and a code; open it in a browser where you are signed in to the hub, check that the code matches and approve. The CLI then receives a token that reaches only the hub's LLM gateway, valid 90 days, and stores it in your user configuration directory, readable by you only. No secret is shipped in the binary: the token stands for your hub account, within its daily quota, and is revoked like any agent token.

probe login                      # https://app.probe.technology by default
probe review --base main         # the reviewer now uses the hub's LLM
probe login --status             # account, model, tokens used today
probe logout                     # revoke the token on the hub and delete it here
FlagDefaultDescription
--hub URLPROBE_HUB_URL, else https://app.probe.technologyThe hub to log in to. HTTPS only, except on the loopback interface. The hub must lend its LLM; otherwise login stops with exit 3.
--statusfalseShow the hub, the account, the model and the tokens used today. Exits 1 when not logged in, or when the login expired or was revoked.
  • The login is used only when nothing else selects a provider: no PROBE_REVIEWER_ENDPOINT, no API key, and a policy endpoint that is OpenAI's default. A configured provider, including a keyless local one, always wins.
  • While it applies, review enables the reviewer automatically, and review --read-only, plan and knowledge build work. The hub's model replaces the policy's, and the console names the hub and the account.
  • Bounded, redacted source context then goes to the hub and its provider. Use --reviewer=false or probe logout to keep it local.
  • In CI, create an LLM gateway token under Agent access in the hub and set it as the PROBE_HUB_TOKEN secret.

Exit codes

CodeMeaning
0Report completed without a reproduced high or critical issue. Without --ci, unresolved areas do not change this code.
1A high or critical hypothesis is supported by a differential failure: a generated test passed on the base and failed on the candidate. Nothing else produces 1 in a review: not a fuzzing divergence, a surviving mutant, a failing impacted or baseline test, plan drift, nor a finding several swarm agents agree on. knowledge check and context check use 1 for an invalid knowledge base or an unavailable context repository.
2With --ci only: human review required, including high-risk signals, unverified areas, incomplete checks, a FAILS_ON_CANDIDATE test, a fuzzing divergence or inconclusive stage, plan drift, a plan that raised a category (the plan gate), or (for plan) a flagged category.
3Invalid arguments, Git comparison, or trusted configuration (including an unknown policy key or command name).
4Operational error in the harness, analysis or report writing, such as Docker or the sandbox image being unavailable, a check that could not run, a failed dependency preparation, or a provider failure during plan.

No code means "approved". A 0 says that nothing was reproduced, not that the change is correct.

Environment variables

The AI provider belongs to the deployment rather than to the repository, so these settings can come from the environment. Nothing else can: the image, commands, budgets and sensitive paths are always decided by the trusted policy.

VariableEffect
PROBE_REVIEWER_ENDPOINTOverrides reviewer.endpoint. Same URL rules as the policy.
PROBE_REVIEWER_MODELOverrides reviewer.model, and on its own enables the reviewer during review.
PROBE_REVIEWER_PROVIDERProvider routing, sent as the request's provider field (OpenRouter). Comma-separated names restrict the request to those providers, in that order; a JSON object is sent as is.
PROBE_REVIEWER_TEMPERATURESampling temperature, 0 to 2. Unset leaves the provider's default.
PROBE_API_KEYAPI key. The name is set by reviewer.api_key_env; this is the default.
PROBE_API_KEY_FILEPath of a file containing the key, used when the variable above is unset. The file must be readable, or the run fails with exit 3.
/run/secrets/PROBE_API_KEYDocker secret read last, when neither variable is set. Absence is not an error.
PROBE_REVIEWER_ALLOW_INSECURE_HTTPtrue permits an explicitly configured http PROBE_REVIEWER_ENDPOINT on a trusted network. Source and key then travel unencrypted.
PROBE_HUB_TOKENAn LLM gateway token created in a Probe Hub, for machines that cannot open a browser, such as CI. It takes precedence over a stored probe login and applies under the same conditions.
PROBE_HUB_URLThe hub of probe login and PROBE_HUB_TOKEN. Default https://app.probe.technology.
PROBE_CREDENTIALS_FILEWhere probe login stores its token, instead of probe/credentials.json in the user configuration directory. off ignores any login.
PROBE_JIRA_URL, PROBE_JIRA_EMAIL, PROBE_JIRA_TOKENJira site for --jira; the e-mail is for Jira Cloud (API token), without it the token is a Server/Data Center personal access token. PROBE_JIRA_CRITERIA_FIELD names an optional acceptance-criteria field.
PROBE_LINEAR_API_KEYLinear key for --linear; a read-only key is enough. PROBE_LINEAR_TEAMS limits the team keys auto accepts.
PROBE_NOTION_TOKENSecret of a Notion integration the pages are shared with, for --notion.
PROBE_GOOGLE_ACCESS_TOKEN, PROBE_GOOGLE_CREDENTIALS, PROBE_GOOGLE_API_KEYFor --gdoc: an OAuth access token, a service-account key file the documents are shared with, or an API key for public documents only.

A blank variable counts as unset. Key files are read whole with surrounding whitespace stripped, bounded to 8 KiB and must hold a single line. The Jira, Linear, Notion and Google tokens and keys may also come from <NAME>_FILE or the Docker secret /run/secrets/<NAME>. When the reviewer runs, the log names where each value came from, never the value itself. Whoever controls this environment chooses where redacted source is sent: keep it out of jobs that run untrusted fork code.

Add .probe/ to .gitignore. The console prints one summary: files and lines changed, number of signals and reproduced issues, the focused review surface and changed-line execution.

Risk signals

Signals are reasons to look, not confirmed defects. Go files get syntax-aware analysis; TypeScript/JavaScript, Python, Rust and other languages use labelled text heuristics. Signals on the same lines are merged into one review range in the report. File-level signals (sensitive_path, dependency_change, migration_change, infrastructure_change, binary_change, file_deleted, file_type_change, large_change, branch_growth, no_test_change, prepare_input_changed, plan_drift) concern the file, not a line: the report lists them under the file as whole file, and the JSON marks them "scope": "file". Their line only places them on the file's first changed line.

Impact analysis

With --impact (the default), lint and review build a static index of the candidate commit on the host, from committed Git objects, without running repository code. For each changed function it lists the places in unchanged code that call it and the existing tests that reach it within 3 calls, adds low impacted_caller signals, and backs the reviewer's find_references, inspect_symbol and find_callers tools.

LanguageHow it is indexedResolution
GoParsed and type-checked with the Go standard library, package by package, with linux/amd64 build constraints. Interface calls are possible dispatch.static, interface
TypeScript/JavaScript, Python, RustScanned lexically: functions, methods and tests are found from tokens, and a call is linked by name to the same-named declarations of the same language, preferring the caller's class, the qualifying module or type and the same file. node_modules, dist, target, venv and similar directories are skipped.name

Every answer is approximate: a listed caller is a place to review, and an absent caller is not proof that none exists. --impacted-tests runs reaching Go tests only. See impact analysis.

Policy file: .probe.json

The policy decides which commands run, in which image, with which limits, and whether an AI provider is used. It is read from .probe.json on the base branch, or from --config PATH. When there is none, built-in defaults for the detected language apply. Keys you omit take the default values shown below.

The file must be a single JSON object of at most 1 MiB. Unknown keys, unknown command names and duplicate keys are rejected with exit 3, so an older binary rejects a key it does not know.

context

A change often depends on contracts that live in another repository: shared types, an SDK, an API client, a sibling service. context names those repositories, directly or through clusters of related repositories, so the reviewer reads them and reports an incompatibility, for example an endpoint the SDK still calls the old way, as an UNVERIFIED hypothesis on the changed line.

"context": {
  "repos": [
    "company/shared-types",
    {"name": "company/payment-sdk", "ref": "main", "paths": ["src/**"], "role": "payment SDK",
     "url": "https://github.com/company/payment-sdk.git"}
  ],
  "clusters": ["payments"],
  "cluster_definitions": {
    "payments": {"description": "Payment service, its SDK and shared types",
                 "repos": ["company/payment-service", "company/payment-sdk", "company/shared-types"]}
  }
}
KeyDescription
context.reposEach entry is owner/repo or an object with name, ref (branch, tag or commit; HEAD by default), paths (globs that restrict what is read), role (for the reviewer) and url.
context.clustersThe clusters this repository belongs to. Every other member becomes context; the repository itself is recognized from its origin remote and left out.
context.cluster_definitionsCluster definitions, or once for a whole organization in an operator file given with --clusters FILE. A cluster defined in both places is refused.

Probe reads the committed files at ref of a local checkout given with --context-dir or --context-repo, never a working tree; with --fetch-context a missing one is shallow-fetched from its url. The reviewer's tools only list, read and search them: sensitive files and files over 1 MiB are never read, nothing is executed, and every read is audited. A repository that cannot be found is recorded as unavailable and never fails the review. Check the setup with probe context check.

AI reviewer

Optional. When a model is configured, review lets it investigate the change with bounded tools: reading redacted files and diffs, searching source, looking up references and callers in the static index, querying the repository graph, reading the context repositories, running existing checks, and creating and running temporary tests on base and candidate. It also receives the knowledge base, the team's coding rules and feedback when they are given. It has no shell and no URL fetcher. Its claims stay hypotheses until a test reproduces a difference.

{
  "reviewer": {
    "endpoint": "https://your-provider.example/v1",
    "model": "your-tool-capable-model",
    "api_key_env": "PROBE_API_KEY"
  }
}
export PROBE_API_KEY=…                       # from your shell or CI secret store
probe review --base main --config .probe.json   # try it before committing
probe review --base main --reviewer=false            # turn it off for one run
  • Only the trusted policy, --config or the deployment environment can enable the reviewer; a pull request cannot.
  • No provider account? probe login lets the reviewer use the LLM of a Probe Hub, within your account's daily quota.
  • Bounded, redacted source context is sent to the provider. Masking of secrets is best effort; use a local provider (for example http://127.0.0.1:1234/v1) if source must stay local.
  • API keys never enter test containers. lint never calls a provider.
  • Provider failures and exhausted budgets keep the deterministic results and mark the investigation incomplete; with --ci that requires human review.

Signal assessments

When the linter raised signals, the reviewer reads each one and gives it a plain-language title stating the intent of the modification ("Admin tokens now skip the expiry check" rather than "Lines added to a sensitive file"), a short explanation and a judgment: risk, no_risk or uncertain. A no_risk reading is kept only when it cites a recorded read of the source. With --ai-impacts-criticality (the default), a kept no_risk lowers its signal by one severity level, the linter's value staying in original_severity, and a low signal is set aside; review targets and the exit code then follow the adjusted severities. The judgment is never evidence and changes no hypothesis status.

Read-only review

probe review --read-only --base main --ci analyzes the diff and the relevant source with the deployment's model, without Docker and without executing repository code. Preparation, checks, coverage, fuzzing and mutation are skipped, and execution flags are refused. The model can read files, get the diff, search code and look up references, symbols, callers and the graph; any write or execution call is rejected.

  • The provider comes from PROBE_REVIEWER_MODEL and PROBE_REVIEWER_ENDPOINT (OpenAI by default), or from a Probe Hub login when neither they nor an API key are set; the policy's reviewer settings are ignored and built-in budgets apply.
  • Suspicions stay UNVERIFIED: no reproduced issue can come from this mode. An unresolved hypothesis still requests human review (exit 2 with --ci).
  • The report records analysis_mode: "review-read-only" and states that no code or test ran.

Reviewer swarm

With --swarm, or a reviewer.swarm policy object, several specialized agents investigate the change in parallel instead of one reviewer. Each is the ordinary reviewer, with the same tools and budgets, plus a focus. Their findings are merged without a model and checked against the evidence like any other: agreement between agents is never evidence.

AgentFocus
correctnessLogic errors, edge cases, broken invariants, regressions of existing behavior.
securityInjection, authentication and authorization bypasses, untrusted input, exposed secrets, unsafe deserialization, SSRF, misused cryptography.
testsWhether tests exercise the changed behavior; weakened or deleted assertions, tests that cannot fail. Writes differential tests where it can.
compatibilityExported APIs, callers in unchanged code, serialized formats, schemas and migrations, contracts with other repositories.
reliabilityError handling, concurrency, resource leaks, timeouts and retries, performance regressions.
intentWhether the change does what its intent asks. Runs only when the intent yielded acceptance criteria.
 
probe review --base main --swarm                               # every agent
probe review --base main --swarm-agents security,correctness   # chosen agents, in this order
probe review --read-only --base main --swarm                   # also in read-only review

A change with more than partition_files changed files has its correctness agent split into up to 4 agents, each owning a group of files. Experiments run one at a time and share one reviewer.max_generated_tests budget; only the model conversations run in parallel, at most max_parallel at a time. If an agent fails, the others' work is kept and the failure is listed. The report lists the agents in reviewer_agents and credits each finding to the agents that submitted it. Provider traffic grows with the number of agents: five agents can cost up to five times one reviewer. See reviewer swarm.

Pull request summary

When the reviewer runs, it writes, after the verdict is settled, a description of the change a person can read in a minute: a title, an overview, changes by area, behavior changes, risks, where to look first, testing, and the developer intentions that group the signals and hypotheses ("Add agent sorting", "Test agent sorting"). It goes to pr_summary in the JSON report, to the top of CONFIDENCE_REPORT.md and to PR_SUMMARY.md, ready to paste as a pull request description.

probe review --base main                       # summary included when the reviewer runs
probe review --base main --pr-summary=false    # skip it
probe report --format pr-summary               # re-render PR_SUMMARY.md from the JSON report

It costs one provider call, two when the first answer is invalid. The summary is model output: it changes no status, severity, review target or exit code, and it is not an approval. A provider failure only leaves it out. Probe publishes nothing; posting it to a pull request is a CI decision. See PR summary.

Team coding rules

--rules TEXT or --rules-file FILE (UTF-8, at most 32 KiB) gives the reviewer your team's coding rules, in both review modes. It checks the changed code, and only the changed code, against them and reports each violation as a hypothesis naming the rule, UNVERIFIED unless evidence supports another status. The rules are review criteria, not instructions: they cannot change the tools, the statuses or the evidence requirements. They come from the command line, never from the reviewed change, and are recorded in coding_rules when a reviewer ran.

probe review --base origin/main --rules-file docs/CODING_RULES.md --ci

Learning from team feedback

--feedback-file FILE (JSON, at most 64 KiB) tells the reviewer what the team thought of earlier findings, so reviews gradually fit the team. Probe Hub builds it from the votes, comments and replies on findings and from whether the next commit changed the flagged file. With at least three reactions and a two-to-one majority, the reviewer is told the trend: it spends less effort on topics the team finds not useful, investigates those it values more deeply, and follows the preferences the comments express.

The feedback is guidance for the model, never evidence. It changes no status, severity or exit code by itself, never justifies dismissing a concrete defect, and is recorded in team_feedback.
